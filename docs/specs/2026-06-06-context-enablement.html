01 The context model: two layers, three scopes

The prompt a provider CLI sees is <product_prompt> + --- + <agent_context>. The product layer is compiled into the app binary; the agent-context layer is assembled from disk at every session start.

ScopeLives inShared byEdited byInjected by
Product app/src-tauri/src/houston_prompt/ every user & agent nobody (binary) env HOUSTON_APP_SYSTEM_PROMPT
Workspace <ws>/WORKSPACE.md · <ws>/USER.md every agent in the workspace user (Settings) + agent (carve-out) workspace_context::build_prompt_section
Agent <agent>/CLAUDE.md · learnings · modes · skills · integrations that one agent user (tabs) + agent (within root) build_agent_context (CLAUDE.md by the CLI)
Key fact Workspace files are never seeded. They exist only once written; until then the prompt renders (empty so far…) so the agent knows the slot exists and is authorized to fill it. This spec adds a proactive path to fill them instead of waiting for the user to type or for the agent to opportunistically capture.

02 How isolation occurs

Three mechanisms. Each agent is walled to its own root; the workspace layer is the single, deliberate hole.

  • Filesystem scoping (the hard wall). First block of every agent prompt = # Working Directory — MANDATORY: all file I/O restricted to <agent-root>. Each agent has its own root, so agents can't see each other's files.
  • The one deliberate hole. build_prompt_section injects parent-dir WORKSPACE.md + USER.md and explicitly authorizes reading/writing those two paths as "an exception to your working-directory rule." Nothing else in the parent is reachable.
  • Session ownership. A per-working_dir guard means one session owns a directory at a time; a second session in the same folder gets a conflict, not a false file-attribution. Different agents/worktrees run in parallel.

Workspace marker = presence of <ws>/.houston/. No marker → build_prompt_section returns None (test dirs and ad-hoc working dirs stay clean).

03 The gap this closes

Onboarding never captures the workspace layer. Today WORKSPACE.md / USER.md fill only two ways, both reactive:

Manual

User hand-types in Settings → Workspace → Shared context (workspace-context.tsx, plain markdown editors over GET|PUT /v1/workspaces/:id/context).

Opportunistic

An agent writes the files mid-chat if the user happens to share something — the passive mechanism the carve-out enables.

Missing No proactive elicitation. No import from existing knowledge. No agent-context estimation. A new user lands in an empty workspace and must either know to fill Settings or hope the agent asks. This spec adds an import-first, proactive enablement flow.

04 The enablement flow

Import-first, ask-residuals-last — not a form. The flow mirrors the workspace's own governance principle: read existing context first, ask the user only for the irreducible residuals.

1
Choose sources. The UI offers folder pick, ~/.claude scan, vault path, and drop-an-export-file. Per-source opt-in. Skippable entirely.
2
Import. Engine parses each source into one bounded, redacted corpus (caps on bytes, file count, token budget). Returns a summary (docs read, bytes, what was skipped and why — surfaced, never swallowed).
3
Synthesize. The corpus runs through the user's already-authed provider CLI as an ephemeral bootstrapper session, returning a ContextDraft = draft USER.md + draft WORKSPACE.md + a list of residual questions. No API keys, data stays local.
4
Ask residuals — including source guidance. Two kinds of question. Content questions fill facts the corpus couldn't answer. Source-hint questions are the agent proactively asking the user where the best rich content lives ("where do you keep your richest project notes?", "is there a folder or notes app I should look at?"). Answering a source-hint with a path loops back to step 2 (import that source) and re-synthesizes. When there was no import at all, fall back to a short fixed content set (role, goals, company, work style, key people, recurring tasks).
5
Review & write. User edits the draft in the same InstructionsContent editor used in Settings, merges in answers, approves. UI assembles the final markdown and calls the existing PUT /v1/workspaces/:id/context. Nothing is written until approval.
Reuse, don't reinvent Synthesis is an engine session, not a new LLM client. The accept step is the existing context route. Reactivity (writes → events → UI refresh) is free. The new surface is just: corpus ingestion + a synthesis prompt + two routes + the wizard UI.

05 Import sources

Five parsers behind one ImportSourceKind enum. All run locally. Web exports are supported as "drop the file you exported" (async — the user does it whenever the export arrives), so they don't block first-run.

KindInputParser doesFirst-run?
LocalFoldera folder pathdepth/size-capped walk over an extension allowlist (.md/.txt/.json/…); flatten to textyes
ClaudeHome~/.clauderead CLAUDE.md + projects/*/memory/* + project role files — already structuredyes (richest)
ObsidianVaulta vault pathwalk .md, keep [[wikilinks]] as entity hintsyes (if path known)
ChatGptExportconversations.jsonparse the export tree, extract message text per conversationasync (emailed)
ClaudeAiExportconversations.jsonparse Claude.ai export, extract message textasync (emailed)
Bounding & safety Every parser enforces caps (max bytes, max files, per-doc truncation) and a token budget on the assembled corpus, plus obvious-secret redaction (API-key / token shaped strings). The corpus is staged on disk, never held only in memory, and is the single input handed to synthesis.

06 Engine surface engine

New module houston-engine-core::context_bootstrap. Two new routes. Accept reuses the existing context route.

Types

// type-safety rule: domain concepts are enums
pub enum ImportSourceKind {
    LocalFolder, ClaudeHome, ObsidianVault, ChatGptExport, ClaudeAiExport,
}
pub struct ImportSource { pub kind: ImportSourceKind, pub path: PathBuf }

pub struct ImportSummary {
    pub docs: usize, pub bytes: u64,
    pub skipped: Vec<SkippedDoc>,   // {path, reason} — surfaced, not swallowed
    pub truncated: bool,
}

pub struct ContextDraft {
    pub user: String,                // draft USER.md
    pub workspace: String,           // draft WORKSPACE.md
    pub questions: Vec<ResidualQuestion>,
}
pub struct ResidualQuestion {
    pub id: String,
    pub prompt: String,
    pub slot: Slot,                  // User | Workspace
    pub kind: QuestionKind,          // Content | SourceHint
}
// Content   = a fact the corpus didn't answer ("what's your role?")
// SourceHint = the agent asking the USER to point it at richer content
//              ("where do you keep your best notes / project docs?").
//              Answering with a path loops BACK into import + re-synthesize.
pub enum QuestionKind { Content, SourceHint }

Synthesis session

Reuses sessions::start with a systemPrompt override + a synthetic session_key, producing no activity card (it must not pollute the board or the assistant's chat history). The bootstrapper prompt instructs: from the material below, draft a short USER.md and WORKSPACE.md and list the residual questions you still need, as a single fenced JSON block, terminated by a [CONTEXT_DRAFT_COMPLETE] marker. The prompt explicitly tells the bootstrapper that when the imported material is thin or absent it should emit SourceHint questions — asking the user to point at where their richest content lives — rather than guessing. A parser extracts the JSON block (same token-detection pattern the onboarding tutorial already uses).

Source guidance (added 2026-06-06) The agent doesn't just ask for facts, it asks the user where to find the best material. A SourceHint answer (a path) re-enters the import → synthesize loop, so a sparse first pass converges by having the user steer the agent to richer sources.

Wire types in houston-engine-protocol; TS methods in @houston-ai/engine-client.

07 App surface app

App-first (extract to ui/ later if mobile needs it). Native pickers are OS glue; everything else composes existing pieces.

Pickers app/src-tauri

Tauri folder/file picker (allowed OS-native glue). Returns path strings to the engine routes. The only Tauri-command surface added.

Wizard app/src/components/context-setup/

source chooser → import progress → synthesize → review/edit (InstructionsContent) → adaptive residual questions → assemble → PUT.

Entry points (one capability, three doors)

  • Onboarding Summary CTA — "Set up your context", optional + skippable (protects the activation metric; core 7-mission flow stays lean).
  • Settings → Shared context empty-state — "Set up automatically" button instead of a bare textarea.
  • Settings → Shared context, non-empty — "Improve" runs the same flow with current content fed back as a source.
Voice rule The UI never says USER.md / files / JSON. It says "tell your assistant about you and your work." (Product-voice invariant — agents' users are non-technical.)
No silent failures Import/synthesis errors surface as toasts with a Report-bug affordance; partial imports report what was skipped and why. No .catch(() => []), no log-and-continue.

08 Privacy model

This reads a non-technical user's personal data (chat history, notes, files). Trust is load-bearing.

  • Explicit per-source opt-in. Nothing is read until the user picks a source and confirms.
  • Local-only processing. Synthesis runs through the user's own authed CLI on their machine. Houston has no server in the desktop loop; the corpus never leaves the device.
  • Disclosure. Each source states what it will read before it runs.
  • Review-before-save. The draft is shown and editable; nothing is written to context until the user approves.
  • Redaction. Obvious secrets are stripped from the corpus before synthesis.
