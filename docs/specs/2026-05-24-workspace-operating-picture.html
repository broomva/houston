Workspace Operating Picture (WOP)

Status: Proposal Date: 2026-05-24 Type: UX + Runtime + Memory Engine Affects: app/, engine/houston-engine-core, engine/houston-skills, ui/board

A proposal to evolve Houston's Activity Board from a kanban over CRUD records into a Workspace Operating Picture — a single primary surface that renders the workspace as a living substrate. Same engine, new ontology. Adds the missing primitives identified in the AI-native assessment: typed Knowledge Graph, first-class Artifacts, agent-curated triage in NOW, and the memory engine that makes them honest at scale.

1. The problem with kanban

Today's Board (@houston-ai/board::AIBoard) renders .houston/activity/activity.json entries as a 4-column kanban (running / needs_you / done / error). It is competent at what it shows. The problem is what it doesn't show — and what it makes invisible by being the primary surface.

The 4-column structure is agent-time, not user-time. needs_you is a status the agent assigned to a session. There is no notion of what the user should look at first — by deal-impact, deadline, blockage. Triage is left entirely to the user's eyes.

And eight load-bearing dimensions of workspace state are invisible:

What the workspace actually containsWhere today's Board shows it
Active sessions (the system's pulse)Hidden behind "running" status
Pending model questionsneeds_you column ✓
Artifacts in motion (drafts, partial outputs)Folded into card; not first-class
Recently settled artifacts"Done" column (as activities, not artifacts)
What the workspace knowsNowhere
Scheduled future workSeparate Routines tab
Integration healthSeparate Connections tab
Agent state (alive / idle / sleeping)Sidebar avatar glow only

The trap: when the Board becomes the model (rather than one view of the model), Houston's session-first engine gets pulled toward project-tracker-shape over time. The kanban is the visible primary surface; the rest of the substrate atrophies behind tabs.

2. The WOP — four regions

Replace (or peer to) the Board tab with a Workspace Operating Picture: one primary surface, four peer regions, each a different face of the workspace state. The kanban becomes one optional toggle inside NOW for users who think in cards.

Each region answers a distinct question:

RegionQuestion it answersPrimitive(s) it surfaces
NOWWhat does the workspace want from me, right now, ordered by what matters?Sessions (live), needs_you items, agent-spotted observations, imminent routines, errors
KNOWINGWhat has the workspace learned, and how do I look at it?Knowledge graph (concept/pattern/fact/entity), provenance links
MAKINGWhat artifacts are in motion, and where are they in their lifecycle?Artifacts (typed, with lineage and lifecycle), file-change events
DOINGWhat is the temporal shape of work — recent, live, scheduled?Session timeline, routine runs, scheduled routines

3. NOW — agent-curated triage

The single most important change. Items in NOW are ranked by the model, not by column status. The model reads WORKSPACE.md, USER.md, the knowledge graph, and active needs_you items, then produces a triage with explicit reasoning attached to each item.

Ranking model

Ranking is a hybrid: agent-curated with deterministic guarantees.

TierWhatDetermined by
R1 (amber, urgent)Errors, blocked-on-deadline items, items the user has explicitly flagged urgentDeterministic: errors auto-promote; deadline within 24h auto-promotes
R2 (amber soft)Standard needs_you items, agent-prioritizedModel-ranked based on context
R3 (green)Imminent scheduled routines (next 24h)Deterministic: routine fire time
R4 (purple)Passive observations the agent surfaced — knowledge-graph hits, suggestions, spotted-during-other-work itemsModel-curated, optional

The deterministic guarantees are load-bearing: no needs_you item is hidden by ranking, errors always appear at R1, the model can only re-order within tiers and surface R4 items. Users can disable R4 entirely ("Houston's attention" slider: terse / balanced / proactive).

The fourth rank is the agentic-native move. R4 items have no equivalent in today's Board because the kanban only renders Activity records. R4 items are things the agent noticed during other work and decided the user might want to know. Calibration is everything — too eager is notification spam; too quiet is invisible value.

4. KNOWING — the substrate, in four lenses

Knowledge has to feel like memory, not a database. Memory is sparse when fresh, dense in places you care about, hazy at the edges, triggered by association. The KG surface must match those qualities at any scale from 0 to 1000+ entities.

The on-disk substrate

Promote learnings from a flat bullet list to a typed entity space. Per-agent learnings stay (working memory); workspace KG is the new layer (long-term semantic memory shared across agents in the workspace). 

~/.houston/workspaces/{Workspace}/
  WORKSPACE.md            # narrative context (already exists)
  USER.md                 # about the human (already exists)
  knowledge/
    concept/<slug>.md    # named ideas
    pattern/<slug>.md    # repeated behaviors / observations
    fact/<slug>.md       # claims w/ provenance
    entity/<slug>.md     # people, companies, products
    index.json            # built index for fast lookup (auto-generated)
    .schema.json          # seeded on first launch

Each entity is markdown with YAML frontmatter, identical in spirit to the broomva-workspace pattern at research/entities/:

---
type: concept
slug: stripe-volume-pricing
title: "Stripe volume pricing"
confidence: 0.85
first_learned: 2026-05-12
last_touched: 2026-05-24
use_count: 7
sources:
  - session: ses_8f3a...
  - session: ses_b21c...
  - file: docs/pricing-research.md
links:
  - concept/pricing-strategy
  - entity/stripe
  - fact/our-current-stripe-tier
status: active             # active | archived | contradicted
contradicts: null          # or another slug
---

# Stripe volume pricing

Stripe applies volume discounts above $1M ARR. The discount is
negotiated, not published. Founders report 15-25% off list at
that tier...

5. KG rendering — four lenses

The same on-disk substrate is rendered through four lenses. The agent decides which lens to default to based on KG scale and current user context.

Lens A — Contextual surfacing (default, always-on)

Knowledge appears inline where it's relevant — in chat, in artifact panels, in needs_you items. Users encounter the substrate by doing work, not by browsing.

Lens B — Wiki-style browser (KNOWING band primary)

For users who want to look. Each entity has a page. Linked entities. Sessions that referenced it. Artifacts that used it. Direct edit.

Lens C — Topic clusters (KG ≥ 50 entities)

Once the KG passes ~50 entities, auto-clustering surfaces topic groupings. Agent-named, user-renamable. Clusters are an agent-decided projection, not the substrate — they're navigation aids, not truth.

Lens D — Graph view (always available, never primary)

Force-directed layout. Node size = use_count. Edge weight = co-occurrence. The graph view is for understanding what's connected, not for browsing what's there. Users open it once or twice a quarter — "what's the shape of what we know?" — and that's fine.

6. KG growth curve — same surface, scale 0 to 1000+

The hardest design constraint: the same KG surface must be honest at scale 0 and scale 1000. Different rendering at different scales. The agent picks the default lens based on entity count + recency profile.

7. MAKING — artifacts in motion

Today, file-creation events emit file_changes feed items with {created: [...], modified: [...]}. The artifact lifecycle is invisible. In WOP, artifacts become a first-class primitive.

On-disk substrate

~/.houston/workspaces/{Workspace}/{Agent}/.houston/
  artifacts/
    artifacts.json          # registry, indexed by id
    artifacts.schema.json
    blobs/                  # snapshots if needed (versions, partials)
      <artifact_id>-v1
      <artifact_id>-v2

Each artifact record:

{
  "id": "art_x9c4...",
  "type": "document",                  // document | dataset | image | code | config | ...
  "title": "NDA draft v3",
  "path": "/Users/.../drafts/nda-v3.md",   // current file path
  "status": "streaming",               // draft | streaming | settled | archived
  "producer_session": "ses_8f3a...",
  "produced_at": "2026-05-24T13:42:00Z",
  "lineage": ["art_x9c2", "art_x9c3"], // parent artifacts (v1 → v2 → v3)
  "uses_knowledge": [
    "concept/nda-standard-terms",
    "concept/two-year-mutual-nda-pattern",
    "fact/our-boilerplate-jurisdiction"
  ],
  "settled_at": null,                  // set when status flips to settled
  "settled_by": null                   // user | agent | timeout
}

8. DOING — temporal worklog

DOING is the temporal lens. Past at left, future at right, live in middle. Replaces today's "Done" column with something browseable. Same data, better representation: every settled session is a marker; scheduled routines are forward markers; the live session sits at now.

9. The memory engine

The KG is markdown files until the engine makes it queryable, decayable, and self-consolidating. Five engine moves turn it from a wiki into substrate.

Total estimate: 11-16 weeks of focused work for one engineer + one designer. Stages 1-4 are the critical path to user-visible value; if forced to ship a slice, ship 1+2+4 (substrate + read path + contextual surfacing) — that's enough to demonstrate the primitive without committing to WOP.

11. Tradeoffs & open questions

WOP vs Board — replace, peer, or kill?

Start as a peer surface ("Workspace" tab next to "Board"). Measure engagement. Decide. Killing the Board before WOP earns its place loses users who genuinely think in cards. There's a real demographic that prefers kanban — power users who manage multiple agents, founders who came from Linear/Jira culture.

Agent-curation vs deterministic guarantees

Pure agent-curated NOW = magical when right, infuriating when wrong. Pure deterministic = transparent but no smarter than today. The hybrid:

  • Deterministic floor — errors always rank 1, no needs_you is hidden, deadlines within 24h auto-promote
  • Agent ceiling — within tiers, agent ranks; surfaces R4 passive observations
  • User dial — "Houston's attention" slider: terse (R1-R2 only) / balanced (default, R1-R4) / proactive (more R4 + suggestion items)

Semantic search cost

Local embedding model (slow on first run, no network, privacy-preserving) vs remote API (recurring cost, faster, privacy implication). Local-first ethos says local model. Memory engine performance depends on this. Real tradeoff.

Open question: which local embedding model ships in the Houston .app? Candidates: all-MiniLM-L6-v2 (small, fast, English-only) · BGE small · Nomic Embed Text v2 (multilingual, 137M params, ~250MB on disk). Multilingual matters because Houston ships en/es/pt. Phase 1 might use OpenAI/Anthropic embeddings API for simplicity, with local model as Phase 2 — but that breaks the local-first promise.

Provenance honesty when user edits

Every entity carries sources. When user edits an entity directly, does it lose machine-confidence? Probably yes (mark confidence: user_override). But this fights the "substrate is user-writable" principle. Worth a real decision before shipping. My instinct: user edits set last_edited_by: user and confidence_source: user, while still preserving machine-derived sources.

Cross-agent shared knowledge governance

When Agent A learns "Acme Corp raised $20M", Agent B in the same workspace should see this. But Agent B may have learned a different fact about Acme Corp. Whose version wins? Per-entity scope tag (workspace vs agent:<id>) is the lever, but the UX for resolving disagreement is unclear. Maybe: workspace-scope entities are merged-on-write with contradiction detection; agent-scope stays separate.

Decay vs forgetting

Should an entity untouched for 12 months be archived (still queryable, hidden from default surfaces) or deleted (gone)? Recommended: archive only, never delete without user confirmation. But this means the substrate grows unboundedly. Compromise: archive after 6mo (no decay before that), warn for deletion after 24mo with explicit user confirmation.

Mobile rendering

The WOP is rich. Mobile gets a stripped version: NOW only (big triage cards, push-style), KNOWING accessible via search but not primary, MAKING/DOING collapsed. Mobile is the "respond to triage on the go" surface; desktop is the substrate. This means the mobile PWA stays useful without becoming the full picture.

Voice rule tension

Houston's voice rule forbids "files, paths, JSON, CLI strings" in user-facing copy. The KG view is, by definition, an exposure of the substrate. Reconciliation:

  • In chat: knowledge chips show title + type icon, never paths. Click → side panel shows body, sources are described ("from your May 12 Stripe call") not pathed
  • In Lens B/C wiki: entity titles are user-facing; slugs are hidden behind hover ("show slug" toggle for developers)
  • Edit experience: markdown editor with title + body fields; frontmatter handled behind the scenes

The substrate stays user-readable for users who want to look (Files tab still shows it), but the default UX never leaks paths.

Net read

The Board is competent SaaS-shape over a genuinely AI-native engine. The WOP + KG rethink is not a rewrite — it is the next layer of legibility over the same substrate. Houston's hardest engineering (files-first, three-writer reactivity, atomic writes, event bus, provider abstraction) already makes everything in this spec possible. What's left is two missing primitives (typed knowledge, lifecycled artifacts) and one cultural shift (agent ranks the user's attention).

The two moves that unlock the rest:

  1. Promote knowledge + artifacts to first-class primitives in .houston/, with the same atomic-writes + schema + event pattern the rest of Houston runs on. Small surface area, big leverage.
  2. Accept agent-curated triage in the primary surface, with deterministic guarantees as backstop. The agent ranks; the system promises no errors and no needs_you items are hidden.

Everything else in this spec — the four lenses, growth curve, WOP regions, memory engine, mobile considerations — is rendering work on top of those two primitives.
